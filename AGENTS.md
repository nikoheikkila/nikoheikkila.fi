# AGENTS.md

This file provides instructions for coding agents when working in this repository.

## Agent Rules

- **Scope**: You are a coding agent for a Gatsby 5 static blog. Your work is limited to source code, tests, content, styles, and infrastructure in this repository.
- **Content safety**: Never modify files under `content/` unless explicitly asked to create or edit content.
- **Infrastructure safety**: Never modify files under `infra/` without using the terraform skill. Always run `task terraform:validate` before proposing infrastructure changes — it works from the repo root.
- **Worker deployments**: Workers are deployed, previewed and deleted only by GitHub Actions through `cloudflare/wrangler-action` (`ci.yml`, `preview-cleanup.yml`). Never run `wrangler deploy`, `wrangler preview`, `wrangler preview delete`, `wrangler versions upload`/`deploy` or `wrangler delete` locally, and never add tasks or scripts that do; the `PreToolUse` hook `.claude/deny-worker-deployments.sh` blocks them. Local `wrangler dev` is fine.
- **Minimal changes**: Prefer the smallest diff that satisfies the request. Do not refactor, add comments, or "improve" surrounding code unless asked.
- **Generated files**: Never hand-edit `src/gatsby-types.d.ts` (generated by `task typegen`) or `test/**/*.spec.js` (Playwright specs generated from `feature/` by `bunx bddgen`).
- **Shell working directory**: Return the shell to the repo root after working in a subdirectory. Hooks and `task` resolve against the current directory — a shell left in a subdirectory makes root tooling (vitest, the root Taskfile) fail confusingly.
- **Workflow diagrams**: Whenever a workflow under `.github/workflows/` or the Terraform actions change, update its diagram in `docs/` to match (`ci.yml`, `lighthouse.yml`, `preview-cleanup.yml` → `docs/ci-flow.svg`; `.github/actions/terraform/*` → `docs/terraform-flow.svg`) and keep the alt text in `README.md` accurate.
- **Local workflow references**: Always reference local reusable workflows and actions as `$/.github/...` (e.g. `uses: $/.github/actions/terraform`), never `./.github/...`. Zizmor enforces this; the `$/` prefix is valid GitHub Actions syntax, not a typo to "fix".
- **Early exit**: If a task is ambiguous or could affect production deployment, stop and ask for clarification rather than guessing.
- **Minimal Verbosity**: Keep output tokens minimal and responses concise. Summarise what changed and why; omit explanations of unchanged code.

## Quick Start

The project is a Gatsby 5 static site generator for a personal blog built with TypeScript, React 19, and Bun. All tasks are run via `task <name>` — use the taskrunner skill (`/taskrunner`) and run `task -a` for the full command reference.

Tool versions are pinned in `mise.toml`, with checksums in `mise.lock`: run `mise install` locally; CI installs them with `jdx/mise-action`. After changing `mise.toml`, run `mise lock` and keep both files in the same commit.

## Architecture Overview

The key architectural decisions are described below.

### Content-First Architecture

- **Markdown-driven content**: Blog posts and pages are written in Markdown with YAML frontmatter in `content/`
- **Programmatic page generation**: Pages are created dynamically in `gatsby/onCreatePages.ts`
- **Gatsby Slices**: Layout components (sidebar menu, footer) use Gatsby's Slices API via `gatsby/slices.ts`
- **GraphQL data layer**: All content is queryable through Gatsby's GraphQL interface
- **30 posts per index page**: Pagination with numbered routes (`/`, `/2/`, `/3/`, etc.)

### Directory Structure

Top-level components in `src/components/`: `elements.tsx`, `hero.tsx`, `schema.tsx` (JSON-LD), `seo.tsx`.

## Development Workflow

### Component Development

- **Modular architecture**: Components are organized by domain (blog, layout, post)
- **TypeScript-first**: All components use TypeScript with generated Gatsby types
- **Custom hooks**: Located in `src/components/hooks/`
- **Icon management**: FontAwesome icons managed through `useIcons` hook
- **Element IDs must use `useId()`**: Biome's `useUniqueElementIds` rule rejects static string `id` attributes. Use `useId()` from React and wire the result to both `id` on the target element and `aria-controls` on the controlling element.

### Styling Approach

Load `styling` skill when you need to work with SASS/SCSS styling in this project.

### Testing Approach

Load `testing` skill when you need to work with unit, component, acceptance, or mutation tests in this project.

#### Acceptance Tests (Playwright BDD)

Acceptance tests are Gherkin scenarios executed by Playwright through [`playwright-bdd`](https://vitalets.github.io/playwright-bdd/). Load the `playwright-bdd` skill when changing user-observable behaviour and the `playwright` skill when writing or debugging step definitions.
- **Source of truth is `feature/`**: scenarios live in `feature/@<domain>/*.feature`, step definitions are decorator-based Page Object Models in `feature/pages/` (`BasePage` for steps common to every page, extended by `HomePage`, `PostPage`, and `NotFoundPage`), registered as fixtures in `feature/fixtures.ts`, with viewports and the `Remembered` state holder in `feature/support.ts`.
- **`test/` is generated output**: `bunx bddgen` (configured by `defineBddConfig` in `playwright.config.ts`) compiles every feature into `test/@<domain>/<name>.feature.spec.js`. The generated specs are gitignored (snapshots under `test/snapshots/` stay tracked); `task test:e2e` regenerates them. Never edit them by hand — `bddgen` deletes and rewrites every `test/**/*.spec.js` on each run.
- **Snapshot baselines survive regeneration**: `test/snapshots/` is hand-maintained and keyed by generated spec path.
- **Run with `task test:e2e`**: it runs `bddgen` before `playwright test` against the production build on port 8000 (`task build` first). Narrow a run by passing generated spec paths or tags, e.g. `task test:e2e -- test/@seo/` or `task test:e2e -- --grep @seo`. Every scenario runs on the `chromium`, `firefox` and `webkit` projects; narrow to one with `-- --project=chromium`. CI builds the site once (`Build` job), then runs one parallel `Acceptance Tests (<browser>)` job per browser.
- **Generated specs stay `.spec.js`**: `playwright-bdd` hardcodes the extension; `test/` is excluded from Biome.

## Deployment

### Hosting Model

- **One path to each environment**: `ci.yml` runs every check (Terraform Plan included) on each pull request and push. For pull requests from this repository (not Dependabot), Preview Deployment runs after the checks and Lighthouse Audit for Preview follows it. On `main` it continues Deploy Infrastructure (`infra/cloudflare`) → Deploy to Production (`wrangler deploy`) → Lighthouse. Deploy Infrastructure runs only when the plan has changes (`needs-apply`). Every Terraform run uses one of the composite actions `.github/actions/terraform/plan` or `/deploy` from a job that checks out the repository, sets up the toolchain, declares its own `environment` and passes credentials as step `env:`; the actions are repository-agnostic and the calling jobs own the project-specific steps.
- **Terraform for infrastructure, Wrangler for the site** — Terraform manages one root module, `infra/cloudflare/` (zone, DNS, redirects, the `blog` R2 bucket, the `nikoheikkila.fi` custom domain for Worker `blog`, and the shared placeholder Worker `blog-preview`). The production Worker `blog` is not Terraform-managed. The site is deployed with Wrangler and Workers static assets (`wrangler.jsonc` at the repo root) by GitHub Actions only, through `cloudflare/wrangler-action`: production on merge to `main`, and Workers Previews for pull requests, which the Cloudflare provider cannot manage. See the terraform skill for commands and provider quirks.
- **Environments**: every pull request from this repository gets a preview (fork and Dependabot pull requests get none), the Workers Preview `pr-<n>` of the shared worker `blog-preview` at `https://pr-<n>-blog-preview.yo-062.workers.dev`, deployed by CI with Wrangler and deleted automatically when the PR closes. A PR closed while its CI still runs gets no preview. `closed` never fires for a PR with merge conflicts: delete its preview with `gh workflow run preview-cleanup.yml -f pull-request=<n>`. There is no per-PR bucket or Terraform workspace. Merging to `main` deploys production with `wrangler deploy` to worker `blog` on `nikoheikkila.fi`.
- **Preview status is a native deployment**: the Preview Deployment job in `ci.yml` runs with `environment: preview`, whose URL is the `preview-url` output of `cloudflare/wrangler-action`, so the pull request shows a "Preview Deployment" check (the name the `Mainline` ruleset requires; a skipped job passes it) and a "View deployment" link. There is no sticky comment or commit status.
- **Trust boundary**: no job that runs pull request code ever gets a `prod` secret. The `preview` environment admits pull request branches, so same-repository pull request runs can reach its `CLOUDFLARE_API_TOKEN`, which is Workers Editor on `blog-preview` only. Fork and Dependabot pull requests never get secrets. The `prod` environment admits only `main` and holds the production and infrastructure tokens. Don't use `pull_request_target` (blocked on public repos from December 2, 2026).
- **Secrets**: 1Password locally: `infra/cloudflare` tasks load `.env.infra`. Previews are deployed and destroyed only by CI. In CI, `CLOUDFLARE_API_TOKEN` is an environment secret in `preview` (Workers Editor on `blog-preview` only, admits pull request branches) and `prod` (Workers Editor on `blog` only, admits `main` only). `prod` also holds `CLOUDFLARE_R2_ACCESS_KEY_ID`/`SECRET` for the Terraform state backend, and `CLOUDFLARE_INFRA_API_TOKEN` for the `ci.yml` Deploy Infrastructure job (`infra/cloudflare` apply), which needs account-wide Workers Scripts Write because Workers Custom Domains have no per-Worker role. The account ID is the non-secret repository variable `CLOUDFLARE_ACCOUNT_ID`, the single source for every tool: CI passes it to Terraform as `TF_VAR_account_id` and to Wrangler as `CLOUDFLARE_ACCOUNT_ID`, and the local Terraform tasks fetch it with `gh variable get`. The preview Worker name (`blog-preview`) is the repository variable `PREVIEW_WORKER_NAME`, used the same way: `TF_VAR_preview_worker_name` for Terraform and `--worker-name` for Wrangler. The repository-level `CLOUDFLARE_READ_API_TOKEN` + `R2_STATE_READ_ACCESS_KEY_ID`/`SECRET` are read-only, for the Terraform Plan job that runs on every CI run.

### Code Quality

- **Biome configuration**: Strict formatting and linting rules (120 char line width)
- **TypeScript strict mode**: Full type safety with generated types
- **JSX conventions**: Classic JSX runtime (`jsx: "react"`), double quotes, trailing commas, tab indentation
- **Import sorting**: Handled by Biome's `useSortedAttributes` assist
- **No unsafe type escapes**: Avoid `as unknown as T` casts and `!` non-null assertions, especially in test mocks/fakes. When faking a large interface but only a few members are actually used (e.g. a Cloudflare `R2Bucket`), implement every member with a correct signature — stub the unused ones so they throw — and type the object directly as the target interface, so no cast is needed. For a value that's provably non-null in context but typed as nullable, construct it so it's non-null by construction (e.g. build a `ReadableStream` directly) instead of asserting `!`.

### File Naming

- **Components**: PascalCase for React components
- **Utilities**: camelCase for utility functions
- **Content**: kebab-case for markdown files
- **Tests**: `*.test.ts` or `*.test.tsx` suffix for unit and component test files; acceptance tests are `kebab-case.feature` files under `feature/@<domain>/` plus PascalCase page models under `feature/pages/`
- **Styles**: `*.module.scss` for component-scoped styles
