# AGENTS.md

This file provides instructions for coding agents when working in this repository.

## Agent Rules

- **Scope**: You are a coding agent for a Gatsby 5 static blog. Your work is limited to source code, tests, content, styles, and infrastructure in this repository.
- **Content safety**: Never modify files under `content/` unless explicitly asked to create or edit content.
- **Infrastructure safety**: Never modify files under `infra/` without using the terraform skill. Always run `task terraform:validate` (and `task site:validate` when `infra/site/` changed) before proposing infrastructure changes — both namespaces work from the repo root.
- **Minimal changes**: Prefer the smallest diff that satisfies the request. Do not refactor, add comments, or "improve" surrounding code unless asked.
- **Generated files**: Never hand-edit `src/gatsby-types.d.ts` (generated by `task typegen`), `infra/site/worker.js` (gitignored, compiled from `worker.ts` by `task site:build`), or `test/**/*.spec.js` (Playwright specs generated from `feature/` by `bunx bddgen`).
- **Shell working directory**: Return the shell to the repo root after working in a subdirectory. Hooks and `task` resolve against the current directory — a shell left in a subdirectory makes root tooling (vitest, the root Taskfile) fail confusingly.
- **Workflow diagrams**: Whenever a workflow under `.github/workflows/` changes, update its diagram in `docs/` to match (`ci.yml` → `docs/ci-flow.svg`, `terraform.yml` → `docs/terraform-flow.svg`) and keep the alt text in `README.md` accurate.
- **Early exit**: If a task is ambiguous or could affect production deployment, stop and ask for clarification rather than guessing.
- **Minimal Verbosity**: Keep output tokens minimal and responses concise. Summarise what changed and why; omit explanations of unchanged code.

## Quick Start

The project is a Gatsby 5 static site generator for a personal blog built with TypeScript, React 19, and Bun. All tasks are run via `task <name>` — use the taskrunner skill (`/taskrunner`) and run `task -a` for the full command reference.

## Architecture Overview

The key architectural decisions are described below.

### Content-First Architecture

- **Markdown-driven content**: Blog posts and pages are written in Markdown with YAML frontmatter in `content/`
- **Programmatic page generation**: Pages are created dynamically in `gatsby/onCreatePages.ts`
- **Gatsby Slices**: Layout components (sidebar menu, footer) use Gatsby's Slices API via `gatsby/slices.ts`
- **GraphQL data layer**: All content is queryable through Gatsby's GraphQL interface
- **30 posts per index page**: Pagination with numbered routes (`/`, `/2/`, `/3/`, etc.)

### Directory Structure

Top-level components in `src/components/`: `elements.tsx`, `hero.tsx`, `schema.tsx` (JSON-LD), `seo.tsx`.

## Development Workflow

### Component Development

- **Modular architecture**: Components are organized by domain (blog, layout, post)
- **TypeScript-first**: All components use TypeScript with generated Gatsby types
- **Custom hooks**: Located in `src/components/hooks/`
- **Icon management**: FontAwesome icons managed through `useIcons` hook
- **Element IDs must use `useId()`**: Biome's `useUniqueElementIds` rule rejects static string `id` attributes. Use `useId()` from React and wire the result to both `id` on the target element and `aria-controls` on the controlling element.

### Styling Approach

Load `styling` skill when you need to work with SASS/SCSS styling in this project.

### Testing Approach

Load `testing` skill when you need to work with unit, component, acceptance, or mutation tests in this project.

#### Acceptance Tests (Playwright BDD)

Acceptance tests are Gherkin scenarios executed by Playwright through [`playwright-bdd`](https://vitalets.github.io/playwright-bdd/). Load the `playwright-bdd` skill when changing user-observable behaviour and the `playwright` skill when writing or debugging step definitions.
- **Source of truth is `feature/`**: scenarios live in `feature/@<domain>/*.feature`, step definitions are decorator-based Page Object Models in `feature/pages/` (`BasePage` for steps common to every page, extended by `HomePage`, `PostPage`, and `NotFoundPage`), registered as fixtures in `feature/fixtures.ts`, with viewports and the `Remembered` state holder in `feature/support.ts`.
- **`test/` is generated output**: `bunx bddgen` (configured by `defineBddConfig` in `playwright.config.ts`) compiles every feature into `test/@<domain>/<name>.feature.spec.js`. The generated specs are gitignored (snapshots under `test/snapshots/` stay tracked); `task test:e2e` regenerates them. Never edit them by hand — `bddgen` deletes and rewrites every `test/**/*.spec.js` on each run.
- **Snapshot baselines survive regeneration**: `test/snapshots/` is hand-maintained and keyed by generated spec path.
- **Run with `task test:e2e`**: it runs `bddgen` before `playwright test` against the production build on port 8000 (`task build` first). Narrow a run by passing generated spec paths or tags, e.g. `task test:e2e -- test/@seo/` or `task test:e2e -- --grep @seo`. Every scenario runs on the `chromium`, `firefox` and `webkit` projects; narrow to one with `-- --project=chromium`. CI builds the site once (`Build` job), then runs one parallel `Acceptance Tests (<browser>)` job per browser.
- **Generated specs stay `.spec.js`**: `playwright-bdd` hardcodes the extension; `test/` is excluded from Biome.

## Deployment

### Hosting Model

- **Terraform first** — Wrangler is used for exactly one thing: uploading preview versions with a preview alias (`task site:ci:preview:upload`), which the Cloudflare provider cannot do. Two root modules: `infra/cloudflare/` (zone, DNS, R2, redirects, Worker custom domain, the shared `blog-preview` Worker) and `infra/site/` (the site itself: build output uploaded to R2, served by a Worker). Shared inputs (`infra/.env`, `infra/cloudflare.tfvars`) live one level up, outside both module directories. See the terraform skill for commands and provider quirks.
- **Environments are Terraform workspaces**: every pull request gets a preview (bucket `site-pr-<n>` plus a version of the shared worker `blog-preview` with preview alias `pr-<n>`, at `https://pr-<n>-blog-preview.yo-062.workers.dev`) deployed by CI; the bucket is destroyed automatically when the PR closes (the alias is left behind); merging to `main` deploys production (worker `blog` on `nikoheikkila.fi`).
- **Preview status is posted as a PR comment**: the `report` job of the `workflow_run` workflow `.github/workflows/preview.yml` (logic in `scripts/preview-report.ts` / `scripts/preview-report/logic.ts`) updates one sticky comment with the preview link on success or the failed step on failure. It runs with its own token, so it also works for Dependabot PRs, whose `pull_request` runs only ever get a read-only token. Fork PRs get no preview.
- **Trust boundary**: no job that runs pull request code ever holds a Cloudflare write token. Write tokens live only in the GitHub environments `preview` and `prod`, which admit deployments from `main` only. The preview deploy and cleanup run trusted code from `main` (`workflow_run`, `pull_request_target`) and treat the PR build artifacts strictly as data. Never check out PR code in those workflows.
- **Secrets**: 1Password (`op run --env-file='.env'`) locally. In CI, `CLOUDFLARE_API_TOKEN` + `CLOUDFLARE_R2_ACCESS_KEY_ID`/`SECRET` are environment secrets in `preview` (Workers Editor on `blog-preview` only) and `prod` (Workers Editor on `blog` only). `prod` also holds `CLOUDFLARE_INFRA_API_TOKEN` for `terraform.yml` deploys of `infra/cloudflare`, which needs account-wide Workers Scripts Write because Workers Custom Domains have no per-Worker role. The repository-level `CLOUDFLARE_READ_API_TOKEN` + `R2_STATE_READ_ACCESS_KEY_ID`/`SECRET` are read-only, for the `terraform plan` on pull requests.

## Key Conventions

### Git Workflow

Load `git` skill ALWAYS before invoking `git` in this repository.

### Code Quality

- **Biome configuration**: Strict formatting and linting rules (120 char line width)
- **TypeScript strict mode**: Full type safety with generated types
- **JSX conventions**: Classic JSX runtime (`jsx: "react"`), double quotes, trailing commas, tab indentation
- **Import sorting**: Handled by Biome's `useSortedAttributes` assist
- **No unsafe type escapes**: Avoid `as unknown as T` casts and `!` non-null assertions, especially in test mocks/fakes. When faking a large interface but only a few members are actually used (e.g. a Cloudflare `R2Bucket`), implement every member with a correct signature — stub the unused ones so they throw — and type the object directly as the target interface, so no cast is needed. For a value that's provably non-null in context but typed as nullable, construct it so it's non-null by construction (e.g. build a `ReadableStream` directly) instead of asserting `!`.

### File Naming

- **Components**: PascalCase for React components
- **Utilities**: camelCase for utility functions
- **Content**: kebab-case for markdown files
- **Tests**: `*.test.ts` or `*.test.tsx` suffix for unit and component test files; acceptance tests are `kebab-case.feature` files under `feature/@<domain>/` plus PascalCase page models under `feature/pages/`
- **Styles**: `*.module.scss` for component-scoped styles
