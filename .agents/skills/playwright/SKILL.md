# End-to-End Testing with Playwright

Acceptance tests are written as Gherkin scenarios and executed by Playwright through `playwright-bdd`. You never write Playwright `test()` blocks by hand — you write scenarios and step definitions, and `bddgen` generates the specs.
- **Scenarios (source)**: `feature/@<domain>/*.feature` — use the `playwright-bdd` skill to add or change them
- **Step definitions (source)**: `feature/@<domain>/steps.ts` (scoped to features in the same directory) and `feature/shared-steps.ts` (shared by all features)
- **Fixtures**: `feature/fixtures.ts` extends the `playwright-bdd` `test` with custom fixtures and exports `Given`, `When`, `Then`
- **Support helpers**: `feature/support.ts` — named page openers (`openPage`), viewports, sidebar helpers, `lookup()`, the shared `links` registry (`link(page, name)`), and the generic `Remembered<T>` state holder behind the `popup`/`fetched`/`destination`/`visit` fixtures used to pass values between steps
- **Generated specs (output)**: `test/@<domain>/<name>.feature.spec.js`, generated by `bunx bddgen` and committed. **Never edit them** — `bddgen` deletes and rewrites every `test/**/*.spec.js` on each run. Regenerate after every `feature/` change and commit the result
- **Snapshot baselines**: `test/snapshots/` is hand-maintained, keyed by generated spec path via `snapshotPathTemplate`, and survives regeneration
- **Configuration**: `playwright.config.ts` — `defineBddConfig()` sets `features`, `steps`, `outputDir: "test"` and `matchKeywords: true`; local/CI environments differ in reporters, timeouts and server reuse
- **Debugging**: the `playwright-test` MCP server (`.mcp.json`) provides browser tools for inspecting pages and locators. Fix failures in `feature/`, run `bunx bddgen`, then re-run

## Running Tests

```shell
task build                                 # E2E runs against the production build on :8000
task test:e2e                              # bddgen + playwright test
task test:e2e -- test/@seo/                # one domain (generated spec path)
task test:e2e -- --grep @seo               # same, by tag (from the @<domain> directory)
task test:e2e -- --grep "Skip link"        # by scenario name
bunx bddgen                                # regenerate test/ only
bunx bddgen export                         # list all registered step definitions
```

`bddgen` fails on missing or ambiguous steps — fix that first; the run never reaches Playwright.

## Writing Step Definitions

```typescript
import { expect, type Page } from "@playwright/test";
import { Given, Then, When } from "../fixtures";
import { lookup, openPage } from "../support";

const searchBox = (page: Page) => page.getByRole("searchbox", { name: "Search" });

Given("the visitor is on the {string}", async ({ page }, name: string) => {
	await openPage(page, name);
});

When("the visitor searches for {string}", async ({ page }, query: string) => {
	await searchBox(page).fill(query);
});

Then("the search results list {int} posts", async ({ page }, count: number) => {
	await expect(page.getByRole("article")).toHaveCount(count);
});
```

- ✅ Import `Given`/`When`/`Then` from `feature/fixtures.ts`, never from `playwright-bdd` directly, so custom fixtures are available
- ✅ `matchKeywords: true` is on: a step is matched by its keyword as well as its text. `And`/`But` inherit the previous keyword. A `Then` definition will not match a `Given` line — define both when a phrase is used as a precondition and an outcome (see `the skip link is focused` in `@accessibility/steps.ts`)
- ✅ Put a step in `feature/@<domain>/steps.ts` when only that domain uses it; move it to `feature/shared-steps.ts` once a second domain needs it. Do not duplicate the same phrase across domains
- ✅ Keep `Given`/`When` steps action-only and put every assertion in a `Then` step
- ✅ Pass values between steps through a fixture from `feature/support.ts` (or a new state-holder class registered in `fixtures.ts`), never module-level variables — tests run fully parallel
- ✅ Map business names in steps to implementation through a `Record` plus `lookup()` (e.g. `openers`, `viewports`, `properties` in `@seo/steps.ts`) so unknown names fail with the list of known ones
- ✅ Extract repeated locators into small `(page: Page) => Locator` functions at the top of the steps file
- ✅ Use `await expect(locator).toBeVisible()` and other auto-retrying assertions
- ✅ Wait for elements to become visible rather than using timeouts
- ✅ **Discover content dynamically**: never hardcode a post slug, title, or other content an editor could rename or reorder. Use the named openers (`"latest post"`, `"oldest post"`, …) or locate structurally — `page.getByRole("article").nth(n)`, a link's `href`
- ✅ Always assert `null`/`undefined` possibilities explicitly (e.g. `expect(response).not.toBeNull()`) instead of narrowing with `if`

### Locator Strategy (Priority Order)

1. **Role-based locators**: `page.getByRole("button", { name: "Submit" })`
2. **Text content**: `page.getByText("Click me")`
3. **Label association**: `page.getByLabel("Email address")`
4. **CSS selectors**: Only as last resort and with specific justification (e.g. `meta` tags, `#main-content`)

### Anti-Patterns

- ❌ Editing anything in `test/**/*.spec.js` — change `feature/` and regenerate
- ❌ Hand-written Playwright `test()`/`test.describe()` specs — every acceptance test starts as a Gherkin scenario
- ❌ `page.waitForTimeout()` - Never use hard-coded timeouts
- ❌ `data-testid` / `data-test-id` - Never add test-id attributes; this project requires web-first locators
- ❌ Inline comments restating what a step's text already says
- ❌ `any` types - Import proper types like `Page` from Playwright
- ❌ `if (!value) throw new Error(...)` inside a step to narrow a value - Use `expect(value).not.toBeNull()`; the state holders in `support.ts` are the only place that throws
- ❌ A scenario that never touches real navigation, network, or browser-only behavior (e.g. it only checks static markup from props) - That belongs in a Vitest component test under `src/__tests__/components/`

### Mobile Viewport Testing

- Use the shared `Given the visitor is browsing on a "phone"` step (375x667, from `viewports` in `support.ts`); add new devices to that registry
- Minimum touch target size: 44px (iOS recommendation)

### Accessibility Testing

- Keyboard navigation must work for all interactive elements (`When the visitor presses "Tab"`)
- Use `toMatchAriaSnapshot` for structure validation
- Verify focus management and skip links functionality

#### Axe-Core Integration

WCAG 2.2 AA scans use `@axe-core/playwright` in the `Then the page has no accessibility violations` step (`feature/@accessibility/steps.ts`). Cover a new page archetype by adding a row to the `Page meets WCAG 2.2 AA` Examples table and, if needed, a named opener in `support.ts`.

```typescript
const WCAG_TAGS = ["wcag2a", "wcag2aa", "wcag21a", "wcag21aa", "wcag22aa"];

Then("the page has no accessibility violations", async ({ page }) => {
	const results = await new AxeBuilder({ page }).withTags(WCAG_TAGS).analyze();

	expect(results.violations).toEqual([]);
});
```

Notes:
- Openers in `support.ts` navigate with `waitUntil: "networkidle"` so React has hydrated and all styles are applied before the scan.
- The `region` rule is tagged `best-practice`, not WCAG — it does **not** run with the WCAG tag filter above.
- Disable a specific rule only when it produces a documented false positive: `.disableRules(["rule-id"])`.
- E2E scans test the full page with production CSS; they catch color-contrast issues that component tests cannot (component tests lack `main.scss`).

### Blog-Specific Patterns

- **Opening pages**: use `openPage(page, name)` from `support.ts`; add new named pages to `openers` there instead of calling `page.goto()` in steps
- **Pagination**: `gotoLastIndexPage` follows `Next Page` links until none remain — reuse it rather than assuming a page count
- **Sidebar menu**: toggle with `toggleSidebarMenu(page)` (role button `Open menu`/`Close menu`) and assert on `sidebarMenu(page)`
- **External links**: capture the popup with `page.waitForEvent("popup")` and store it in the `popup` fixture for later `Then` steps; stub the external host with `context.route()` so the test never hits the live site
- **Navigation gotcha**: `page.waitForURL(/\//)` matches almost any URL, including the current one. When the destination isn't a specific known pattern, capture the link's `href` (the `destination` fixture) and assert or `goto()` it directly

## Troubleshooting

- **Missing step / ambiguous step from `bddgen`**: the Gherkin line has no definition with a matching keyword, or two definitions match. Check `matchKeywords` (keyword must match), the directory scope, and `bunx bddgen export`
- **Change in `feature/` has no effect**: `test/` was not regenerated — run `bunx bddgen` (or `task test:e2e`, which does it for you)
- **Stale or orphaned snapshot**: snapshot paths follow the generated spec path; renaming a feature file or directory moves its baseline under `test/snapshots/`
- **E2E test failures**: Ensure a production build exists and is served from <http://localhost:8000>
- **Component changes**: Always run `task build` after modifying React components before running E2E tests
- **Test timeouts**: 60s per test in CI, Playwright default locally
- **Clicks do nothing**: page not hydrated yet — navigate with `waitUntil: "networkidle"` (the `support.ts` openers already do)
- **API tests (robots.txt, sitemap)**: These files are only generated in production builds
