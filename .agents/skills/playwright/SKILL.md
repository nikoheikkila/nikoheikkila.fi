# End-to-End Testing with Playwright

Acceptance tests are written as Gherkin scenarios and executed by Playwright through `playwright-bdd`. You never write Playwright `test()` blocks by hand — you write scenarios and step definitions, and `bddgen` generates the specs.
- **Scenarios (source)**: `feature/@<domain>/*.feature` — use the `playwright-bdd` skill to add or change them
- **Step definitions (source)**: decorator-based Page Object Models in `feature/pages/`. `BasePage` holds the steps that are common to every page (openers, links, search, RSS feed, sidebar menu, footer, skip link, cover image, external links, metadata, feeds); `HomePage`, `PostPage`, and `NotFoundPage` extend it with page-specific steps. Page models live outside `@<domain>` directories, so their steps are global
- **Fixtures**: `feature/fixtures.ts` registers each page model as a fixture (`basePage`, `homePage`, `postPage`, `notFoundPage`) in `test.extend`
- **Support helpers**: `feature/support.ts` — `viewports` and the generic `Remembered<T>` state holder used for page model fields that pass values between steps
- **Generated specs (output)**: `test/@<domain>/<name>.feature.spec.js`, generated by `bunx bddgen` and gitignored. **Never edit them** — `bddgen` deletes and rewrites every `test/**/*.spec.js` on each run. Regenerate after every `feature/` change
- **Snapshot baselines**: `test/snapshots/` is hand-maintained, keyed by generated spec path via `snapshotPathTemplate`, and survives regeneration
- **Configuration**: `playwright.config.ts` — `defineBddConfig()` sets `features`, `steps`, `outputDir: "test"` and `matchKeywords: true`; local/CI environments differ in reporters, timeouts and server reuse. Three projects (`chromium`, `firefox`, `webkit`) run every scenario; `webkit` skips `@tabs-to-links` scenarios because WebKit, like Safari, does not Tab-focus links
- **Debugging**: the `playwright-test` MCP server (`.mcp.json`) provides browser tools for inspecting pages and locators. Fix failures in `feature/`, run `bunx bddgen`, then re-run

## Running Tests

```shell
task build                                 # E2E runs against the production build on :8000
task test:e2e                              # bddgen + playwright test
task test:e2e -- test/@seo/                # one domain (generated spec path)
task test:e2e -- --grep @seo               # same, by tag (from the @<domain> directory)
task test:e2e -- --grep "Skip link"        # by scenario name
task test:e2e -- --project=chromium        # one browser
bunx bddgen                                # regenerate test/ only
bunx bddgen export                         # list all registered step definitions
```

`bddgen` fails on missing or ambiguous steps — fix that first; the run never reaches Playwright.

## Writing Step Definitions

```typescript
import { expect } from "@playwright/test";
import { Fixture, Then } from "playwright-bdd/decorators";
import type { test } from "../fixtures";
import { BasePage } from "./BasePage";

@Fixture<typeof test>("homePage")
export class HomePage extends BasePage {
	@Then("the visitor sees {int} posts")
	public async expectPostCount(count: number): Promise<void> {
		await expect(this.articles).toHaveCount(count);
	}
}
```

- ✅ Import `Fixture`/`Given`/`When`/`Then` from `playwright-bdd/decorators`. Type the fixture name with `@Fixture<typeof test>("…")` via `import type { test } from "../fixtures"` and register every new page model in `fixtures.ts`
- ✅ Decorator methods receive only step parameters — reach the browser through `this.page`
- ✅ Stack decorators on one method when several phrases share an implementation (e.g. `BasePage.openHomePage` handles both `the visitor is on the home page` and `the visitor opens the home page`)
- ✅ `matchKeywords: true` is on: a step is matched by its keyword as well as its text. `And`/`But` inherit the previous keyword. A `Then` definition will not match a `Given` line — define both when a phrase is used as a precondition and an outcome (see `the skip link is focused` in `BasePage`)
- ✅ Put a step on the page model where the behaviour lives; put it on `BasePage` when every page has it. Do not duplicate the same phrase across page models
- ✅ A `BasePage` step runs on the child page fixture when the scenario uses steps from exactly one child page, and on the `basePage` fixture otherwise. `BasePage` therefore stays a concrete `@Fixture`, and state written by a `BasePage` step must only be read by `BasePage` steps
- ✅ Keep `Given`/`When` steps action-only and put every assertion in a `Then` step
- ✅ Pass values between steps through a private `Remembered<T>` field on the page model, never module-level variables — tests run fully parallel
- ✅ Give each business concept its own literal step and method (e.g. `the visitor follows the link to the next index page`) instead of a `{string}` parameter resolved through a name registry. Scenario Outlines still work: `bddgen` substitutes `<placeholder>` values before matching, so `opens the <page>` matches `opens the home page`. Quote parameters only for free-form values (paths, search terms, keys, expected text)
- ✅ Extract repeated locators into private getters on the page model
- ✅ Use `await expect(locator).toBeVisible()` and other auto-retrying assertions
- ✅ Wait for elements to become visible rather than using timeouts
- ✅ **Discover content dynamically**: never hardcode a post slug, title, or other content an editor could rename or reorder. Use the named opener steps (`the latest post`, `the oldest post`, …) or locate structurally — `page.getByRole("article").nth(n)`, a link's `href`
- ✅ Always assert `null`/`undefined` possibilities explicitly (e.g. `expect(response).not.toBeNull()`) instead of narrowing with `if`

### Locator Strategy (Priority Order)

1. **Role-based locators**: `page.getByRole("button", { name: "Submit" })`
2. **Text content**: `page.getByText("Click me")`
3. **Label association**: `page.getByLabel("Email address")`
4. **CSS selectors**: Only as last resort and with specific justification (e.g. `meta` tags, `#main-content`)

### Anti-Patterns

- ❌ Editing anything in `test/**/*.spec.js` — change `feature/` and regenerate
- ❌ Hand-written Playwright `test()`/`test.describe()` specs — every acceptance test starts as a Gherkin scenario
- ❌ `page.waitForTimeout()` - Never use hard-coded timeouts
- ❌ `data-testid` / `data-test-id` - Never add test-id attributes; this project requires web-first locators
- ❌ Inline comments restating what a step's text already says
- ❌ `any` types - Import proper types like `Page` from Playwright
- ❌ `if (!value) throw new Error(...)` inside a step to narrow a value - Use `expect(value).not.toBeNull()`; `Remembered` in `support.ts` is the only place that throws
- ❌ A scenario that never touches real navigation, network, or browser-only behavior (e.g. it only checks static markup from props) - That belongs in a Vitest component test under `src/__tests__/components/`

### Mobile Viewport Testing

- Use the shared `Given the visitor is browsing on a phone` step (375x667, from `viewports` in `support.ts`); add a new device to `viewports` together with its own step
- Minimum touch target size: 44px (iOS recommendation)

### Accessibility Testing

- Keyboard navigation must work for all interactive elements (`When the visitor presses "Tab"`)
- Use `toMatchAriaSnapshot` for structure validation
- Verify focus management and skip links functionality

#### Axe-Core Integration

WCAG 2.2 AA scans use `@axe-core/playwright` in the `Then the page has no accessibility violations` step (`BasePage`). Cover a new page archetype by adding a row to the `Page meets WCAG 2.2 AA` Examples table and, if needed, a named opener step in `BasePage`.

```typescript
const WCAG_TAGS = ["wcag2a", "wcag2aa", "wcag21a", "wcag21aa", "wcag22aa"];

@Then("the page has no accessibility violations")
public async expectNoAccessibilityViolations(): Promise<void> {
	const results = await new AxeBuilder({ page: this.page }).withTags(WCAG_TAGS).analyze();

	expect(results.violations).toEqual([]);
}
```

Notes:
- `BasePage.goto()` navigates with `waitUntil: "networkidle"` so React has hydrated and all styles are applied before the scan.
- The `region` rule is tagged `best-practice`, not WCAG — it does **not** run with the WCAG tag filter above.
- Disable a specific rule only when it produces a documented false positive: `.disableRules(["rule-id"])`.
- E2E scans test the full page with production CSS; they catch color-contrast issues that component tests cannot (component tests lack `main.scss`).

### Blog-Specific Patterns

- **Opening pages**: add a named opener method to `BasePage` with stacked `@Given("the visitor is on the …")` / `@When("the visitor opens the …")` decorators; reuse it (e.g. `this.openHomePage()`) from other steps
- **Pagination**: `BasePage.gotoLastIndexPage()` reads the page count from the home page's `Next Page (2/N)` link and opens `/N/` — reuse it rather than assuming a page count
- **Sidebar menu**: `BasePage` toggles it with `toggleSidebarMenu()` (role button `Open menu`/`Close menu`) and asserts on the `sidebarMenu` getter
- **External links**: capture the popup with `page.waitForEvent("popup")` and store it in `BasePage`'s `popup` field for later `Then` steps; stub the external host with `context.route()` so the test never hits the live site
- **Navigation gotcha**: `page.waitForURL(/\//)` matches almost any URL, including the current one. When the destination isn't a specific known pattern, capture the link's `href` (`BasePage`'s `destination` field) and assert or `goto()` it directly

## Troubleshooting

- **Missing step / ambiguous step from `bddgen`**: the Gherkin line has no definition with a matching keyword, or two definitions match. Check `matchKeywords` (keyword must match) and `bunx bddgen export`. "No POM fixtures found" means a page model is missing `@Fixture` or its `fixtures.ts` registration
- **Change in `feature/` has no effect**: `test/` was not regenerated — run `bunx bddgen` (or `task test:e2e`, which does it for you)
- **Stale or orphaned snapshot**: snapshot paths follow the generated spec path; renaming a feature file or directory moves its baseline under `test/snapshots/`
- **E2E test failures**: Ensure a production build exists and is served from <http://localhost:8000>
- **Component changes**: Always run `task build` after modifying React components before running E2E tests
- **Test timeouts**: 60s per test in CI, Playwright default locally
- **Clicks do nothing**: page not hydrated yet — navigate with `waitUntil: "networkidle"` (`BasePage.goto()` already does)
- **API tests (robots.txt, sitemap)**: These files are only generated in production builds
